# HTML 合并为单文件：性能影响分析与实现方案

> 项目：南昌基地特化 · 客舱培训系统
> 分析对象：根目录 13 个活跃 HTML 页面（合计 73.87 MB）
> 配套工具：`_merge_html.cjs`（合并）、`_merge_bench.cjs` / `_merge_bench_full.cjs`（实测）
> 实测环境：Microsoft Edge + playwright-core，file:// 协议，1440×900 视口
> 日期：2026-10-12

---

## 0. 结论摘要

| # | 结论 |
|---|---|
| 1 | 本项目 13 个页面 **CSS/JS 已全部内联、图片多为 base64**，"合并"的实质是把 13 个自包含文档拼成一个 73.9 MB 的单文件 SPA。 |
| 2 | **小集合合并（≤5 页、总量 <1 MB）实测更快**：3 页演示中单文件加载 97 ms vs 多页面 3 次导航合计 316 ms（0.31×），且功能零损失（JS 错误 0、文本内容逐字符一致）。 |
| 3 | **全量合并（74 MB）不可取**：任何入口都要先下载+解析全部 13 页。轻度用户（只开 report.html）从 89 ms / 52 KB 恶化为 1,716 ms / 73.9 MB（**19× 耗时、1420× 字节**）；JS 堆 159 MB。 |
| 4 | 合并的固有代价已量化：32 组 ID 冲突、15 组全局符号冲突、248 个跨页同名 class——工具可自动处置大部分，但全局符号冲突需人工确认。 |
| 5 | **建议**：保留多页面架构；若确需单文件交付，只合并小页面子集（如 report/manual/issues 这类 <200 KB 的工具页，产物 0.34 MB），并启用工具的作用域隔离与 ID 前缀化。 |

### 1.2 架构特征（决定了合并分析的特殊性）

1. **零外链资源**：13 个页面均无 `<link rel="stylesheet">`、无 `<script src>`（仅 daily/qa 有 2~3 个外站超链接）。每个页面打开 = **恰好 1 个网络请求**。
2. **图片全部 base64 内嵌**：cc-home 96%、daily 92%、qa 71%。体积大头是二进制素材而非代码。
3. **页面间跳转靠 JS**：`location.href = id + '.html'`（kb-admin）、`window.open('cc-home.html', …)`（qa）。
4. **已有 Service Worker**（`sw-quiz.js`）：stale-while-revalidate 策略缓存同源 GET 请求，版本号 `spring-quiz-v10-offline-2026`。
5. **页面已内置"壳层自检"**：各页 head 首行均有 `__EMBED_SELF_20261009__` 检测（`window.self !== window.top` 时隐藏自带顶栏）——说明项目此前已尝试过壳层化嵌入（`_bak_20261009_embed/` 留有备份）。

> 关键推论：由于每页本来就是 1 个请求，"合并减少请求数"在本项目**不成立**（1 → 1）。合并的唯一收益是"少几次浏览器导航开销"，唯一代价是" payload 从按需变为全量"。这与传统"多文件 CSS/JS 合并"场景有本质区别。

## 2. 五维度影响分析

### 2.1 页面加载速度

**多页面（现状）**：每次导航只传输目标页面。传输量 = 用户实际访问页面的字节和，与未访问页面无关。

**单文件（合并后）**：任何入口、任何跳转都是 0 次额外请求，但首次打开必须完整传输 73.94 MB（13 页拼接 + 约 0.9% 外壳开销）。

**量化对比**（三类典型用户旅程）：

| 用户旅程 | 多页面传输量 | 单文件传输量 | 倍数 |
|---|---:|---:|---:|
| 轻度：首页 → 事件报告 → 手册 | 636 KB | 73.94 MB | **116×** |
| 中度：首页 → 美妆 → 测验 → 报告 | 7.69 MB | 73.94 MB | **9.5×** |
| 重度：13 页全部访问 | 73.87 MB | 73.94 MB | 1.0×（持平） |

**传输耗时估算**（纯网络时间，不含解析）：

| 带宽 | 636 KB（轻度·多页面） | 73.94 MB（单文件） |
|---|---:|---:|
| 100 Mbps | 0.05 s | **5.9 s** |
| 10 Mbps | 0.51 s | **59.2 s** |
| 4G 实测 ~8 Mbps | 0.64 s | **73 s** |

**实测佐证**（file:// 本地，排除网络变量，仅剩磁盘 I/O + 解析）：
- 3 页小集合：多页面 3 次导航合计 316 ms，单文件 1 次 97 ms → **小集合下单文件反而快 3.3×**（省掉 2 次浏览器导航/文档建立开销）。
- 全量 13 页：多页面 13 次导航合计 3,284 ms（均页 253 ms），单文件 74 MB 一次加载 1,716 ms——**单文件首次加载 = 多页面平均单页的 6.8×**。若用户只打开最轻的 report.html（89 ms），单文件方案要付出 1,716 ms（19×）。

**结论**：加载速度的利弊完全由"访问页数 × 页面体积分布"决定。页面少而小 → 合并占优；访问稀疏或体量大 → 合并灾难性劣化。本项目 qa.html 单页 32 MB、cc-home 23 MB，属于典型"访问稀疏 + 单体巨大"，全量合并严重劣化加载速度。

### 2.2 浏览器解析与渲染过程

**多页面**：浏览器每次只面对一个文档（0.4~4.4 MB 常见，最大 qa 32 MB）。HTML 解析 → CSSOM 构建 → 渲染树 → 布局 → 绘制的链路短，未访问页面的代码/样式完全不参与解析。

**单文件**：一个 73 MB 文档带来的链式成本：

1. **HTML 分词全量进行**：73 MB 文本需完整分词才能确定文档结构；base64 属性值极长，分词器状态机开销随文档增大超线性上升。
2. **CSSOM 全局合并**：97 个 `<style>` 块（约 1.2 MB 样式 + 内嵌图片 URI）全部进入同一个 CSSOM，选择器匹配范围覆盖全部 13 页的 DOM。
3. **DOM 一次性全量构建**：13 页的元素同时存在于文档树。实测：3 页演示合并后 DOM 5,208 节点 vs 多页面峰值 5,011（+3.9%）；**13 页全量合并后 DOM 16,780 节点**（约为最重单页 manual 的 3.3 倍），样式计算与布局范围覆盖全部页面。
4. **脚本执行语义变化**：15 个脚本块全部在首次加载时执行（已实测 0 语法错误），但——
   - 各页脚本中对 `document.body`、`window` 的假设在共享文档下互相干扰；
   - 实测发现 **15 组全局符号跨页重复定义**（`window.PACKS` 5 页、`window.QaLanding` 6 页、`window.fetch` 6 页被猴补丁……），后者静默覆盖前者，行为难以预测；
   - 布局测量类代码（offsetWidth 等）在路由激活前对隐藏 section 测量会得到 0。
5. **内存放大**：文本 → DOM 节点通常有 3~10 倍内存放大；74 MB 文本 + 49.4 MB base64 解码后的位图。**实测单文件 JS 堆峰值 159.3 MB**（Edge），而多页面模式任一页面 heap 均在个位数 MB 量级。

**结论**：合并把"按需解析一个文档"变成"一次性解析全部文档"。解析、样式计算、布局、内存四个环节全部从 O(单页) 恶化到 O(全集)。小集合（3 页）实测增量仅 +4%，可接受；13 页全量则把最重页面（qa 32 MB）的解析成本强加给每一次打开。

### 2.3 首屏时间（FCP）

**多页面**：FCP = 下载目标页 + 解析目标页 + 首次绘制。打开 report.html（52 KB）与打开 qa.html（32 MB）的首屏代价相差三个数量级，但用户只为当前页面付费。

**单文件**：FCP = 下载 73.94 MB + 解析 73.94 MB + 路由外壳渲染。**任何入口的首屏都被拉平到全集上限**——想只看 52 KB 的报告页，也要先等 74 MB 到位（除非做代码分割，而那样就不再是"单文件"）。

**实测**（3 页演示，file:// 本地）：
- 多页面打开 issues.html：wall 64 ms、DCL 14 ms；
- 单文件打开（含 report+manual+issues 全部内容）：wall 97 ms、DCL 27 ms；
- 单文件内路由切换（hash 变更，无网络）：28~131 ms（manual 内容最多，切换后重排代价最高）。

本地盘下差距仅 1.5×；一旦放到 10 Mbps 网络，单文件首屏 ≈ 59 s 传输 + 数秒解析，而多页面首屏仍为亚秒级。**首屏时间是合并受损最严重的维度**：它从"按需"变成"预付"。

---

### 2.4 缓存利用率

**多页面**：13 个文档独立缓存。HTTP 缓存 / Service Worker（`sw-quiz.js` 已实现 stale-while-revalidate）按 URL 粒度生效：
- 只访问过 3 页的用户，缓存里只有那 3 页（约 0.65 MB）；
- 修改 report.html 只令该文件失效，其他 12 页缓存照用；
- 版本升级只需重传变化页面。

**单文件**：全部内容一个缓存实体：
- 任何局部修改（哪怕只改 report 一段文字）都改变整个 73 MB 文件的哈希/时间戳 → **所有客户端全量重下 73 MB**；
- 只访问 3 页的用户也被迫缓存 73 MB（**112× 存储浪费**）；
- 缓存配额风险：移动端浏览器对单源缓存有限制（Safari 等对 Cache API 容量敏感），74 MB 实体可能被整体驱逐，反而丢掉离线能力；
- SW 的 `CACHE_NAME` 版本号机制（当前 `spring-quiz-v10-offline-2026`）在单文件下意味着一次发版 = 一次 74 MB 全网重下。

**结论**：缓存维度是合并**净损失最明确**的一项——更新粒度从"页"退化为"全站"，存储占用从"按需"退化为"全量"。本项目页面更新频繁（备份目录中可见同一天多次改动 beauty/performance/index），该维度损失会被持续放大。

---

### 2.5 后续维护成本

**多页面（现状）的成本**：
- 共享代码（顶栏、主题变量、QaLanding 组件）在 13 页间复制粘贴，存在**漂移风险**——实测 367 个 class 跨页同名、15 组全局符号重复定义即是漂移的存量证据；
- 但：单页可独立打开、独立测试、独立回滚；项目已有的 `_patch_*.cjs` 补丁脚本、`.bak_*` 备份体系全部围绕单页文件构建。

**单文件的成本**：
- 获得单一事实来源（共享顶栏/样式只写一次）；
- 但引入**构建链路**：源页面 → 合并产物必须工具化（本报告 §4 即为此而生），日常改动从"改一个 HTML"变成"改源页 + 跑合并 + 验证产物"；
- 74 MB 单文件对编辑器/git 都不友好（ diff 噪声大、合并冲突概率高）；
- 合并固有问题需长期对抗：ID 前缀化后人工排查元素引用变困难；全局符号冲突只能告警不能自动修；
- 调试时控制台堆栈指向 74 MB 文件中的某一行，定位成本高于 13 个语义化文件名。

**实测数据**：合并工具 16 ms 完成 3 页合并、约 1.4 s 完成 13 页合并——构建本身不慢；真正的成本在"碰撞处置 + 产物验证 + 工作流改造"。

**结论**：维护维度不是单向优劣，而是**成本结构迁移**：从"跨页复制粘贴的漂移成本"迁移到"构建链路 + 巨文件操作 + 碰撞治理成本"。对本项目（已有成熟单页补丁/备份工作流、页面更新频繁），迁移的净收益为负。

## 3. 适用场景总结

| 场景 | 建议 | 理由 |
|---|---|---|
| 页面少（≤5）、总量小（<1 MB）、无后续局部更新 | **适合合并** | 请求/导航开销占比高，合并实测更快（3 页演示 0.3×）；缓存损失可忽略 |
| 单次交付的离线产物（发给同事的一个清单/报告 HTML） | **适合合并** | 无缓存复用需求，"一个文件"的交付体验优先 |
| 页面体量大且访问稀疏（本项目：qa 32 MB、cc-home 23 MB） | **禁止全量合并** | 轻度用户传输放大 116×，首屏/缓存双输 |
| 频繁局部更新、依赖增量缓存 | **禁止合并** | 一次改动触发全量重下 |
| 多页共享大量 UI 代码、存在严重复制粘贴 | **部分受益** | 可抽取共享层为独立缓存文件（传统方案），而非拼成单文件 |
| 移动端/弱网/存储敏感客户端 | **禁止合并** | 74 MB 实体传输与缓存配额风险 |

**本项目结论**：保留多页面架构。如确有单文件需求，只合并 report/manual/issues 这类小工具页子集（0.35 MB，实测零功能损失），**不要**全量合并 13 页。

## 4. 实现方案：`_merge_html.cjs`

技术上完全可行，已实现并通过浏览器验证。

### 4.1 合并策略

```
输入: N 个自包含 HTML（每页 head 样式/脚本 + body 内容 + base64 图片）
          │
          ▼
   线性文档解析 ────┬─ <title> / data-theme（路由时恢复每页主题）
   （非正则，与浏览器  ├─ <style> 块（head 进公共样式区，body 原位保留）
    一致地跳过脚本/   ├─ <script> 块（去 src 外链后按页收编为一个 IIFE）
    样式原始文本中     └─ body HTML（section 化）
    的伪标签）
          │
          ▼
   变换层 ────────┬─ CSS 作用域化：选择器加 #pg-<页名> 前缀（默认开启）
                 ├─ ID 前缀化：跨页冲突 id 加 <页名>-- 前缀（含 for/href/JS 引用）
                 ├─ 导航重写：href="x.html"→#/x；location.href/window.open→__nav('x')
                 └─ 碰撞检测：id / 全局符号 / class 三类，告警上报
          │
          ▼
   外壳组装 ──────┬─ 顶部模块导航栏（sticky）
                 ├─ hash 路由 #/<页名>（hashchange 驱动，切页重置滚动/标题/主题）
                 └─ 每页一个 <section class="pg" id="pg-<页名>">
```

**关键设计决策**：
1. **线性文档解析器而非正则**：实测 performance.html 的 SheetJS 脚本字符串内嵌 `</head>`/`<body>`/`</body>` 文本、多页 `<style>` 出现在 `<script>` 字符串内——正则切分会发生 head 截断（JS 变 body 裸文本）或把 JS 当 CSS 注入 `#pg-` 前缀。解析器按 HTML 规范线性扫描，只在正常内容流识别真标签，与浏览器行为一致。
2. **脚本按页合并为单个 IIFE**：页内多个脚本块原本共享文档顶层词法作用域（如 index.html 的 `let currentMod` 跨块可见），逐块包裹会破坏该语义；按页包裹后页内共享、跨页隔离，与多页面文档行为一致。整体置于 body 尾部执行。
3. **CSS 默认作用域隔离**：解析器感知字符串/注释/@media 递归，`html`/`body`/`:root` 选择器重定向到 section，`html[data-theme="dark"] .x` 重定向为 `html[…] #pg-x .x`——248 个跨页同名 class 因此互不污染。
4. **ID 冲突自动前缀化**：覆盖 `id=`/`for=`/`href="#id"`/`getElementById`/`querySelector('#id')`/`$('#id')`，并识别各页自定义的 `$ = id => document.getElementById(id)` helper 后追加 `$('id')` 形式。
5. **导航三形态重写**：静态 href、`location.href='x.html'`（含模板串 `\'x.html\'` 写法）、`window.open('x.html', …)`（整体调用含第二参数）；动态导航（`location.href=expr+'.html'`）检测后告警，交人工改造。

### 4.2 碰撞处置实测（13 页全量）

| 碰撞类型 | 数量 | 处置 |
|---|---:|---|
| 跨页重复 ID | 32 组 | 自动加页面前缀（如 `uxPolish` 出现在 11 页 → `index--uxPolish`…） |
| 跨页重复全局符号 | 15 组 | **仅告警**（`window.PACKS`/`QaLanding`/`fetch`/`CC3D` 等，后者覆盖前者，需人工确认） |
| 跨页同名 class | 248 个 | CSS 作用域隔离（`--no-scope` 可关闭，关闭后按级联合并） |
| 外链资源 | 0 | 本项目无外链 CSS/JS，无需内联 |
| 动态导航 | kb-admin 等 | 告警（`location.href=id+'.html'` 无法静态改写） |
| type="module" 脚本 | 0 | 如有则单独包裹并告警 |

### 4.3 实测验证

**3 页演示集**（report + manual + issues，输入 0.33 MB → 输出 0.34 MB，外壳开销 +1.05%）：

| 指标 | 多页面（3 次导航） | 单文件（1 次加载） |
|---|---:|---:|
| 加载 wall 耗时 | 316 ms | **97 ms（0.31×）** |
| DCL 累计 | 57 ms | 27 ms |
| DOM 节点峰值 | 5,011 | 5,208（+3.9%） |
| JS 堆占用 | — | 9.5 MB |
| JS 错误数 | 0 | **0** |
| 内容完整性 | 文本 368 / 34,801 / 403 字符 | 与多页面**逐字符一致** |
| 路由切换 | — | 28~131 ms/次，三页均可见、标题正确 |

**13 页全量**（73.87 MB → 73.94 MB，外壳开销 +0.1%）：

| 指标 | 多页面 | 单文件合并 | 差异 |
|---|---:|---:|---:|
| 首次加载 wall | 均页 253 ms（13 页共 3,284 ms） | **1,716 ms** | 均页的 **6.8×** |
| 只开 report.html | 89 ms / 52 KB | 1,716 ms / 73.9 MB | **19× 耗时 / 1420× 字节** |
| DOM 节点 | 单页最多 5,011 | **16,780** | 全量共存 |
| JS 堆峰值 | 个位数 MB | **159.3 MB** | — |
| JS 错误数 | 0 | **0**（15 个脚本块全部通过语法检查） | 功能等价 |
| 路由切换 | 整页导航 64~654 ms | 47~163 ms | 合并后切换更快 |
| base64 完整性 | 49,403,935 字符 | 49,403,659 字符 | **无丢失** |

**功能保真度说明**：
- body 子代选择器（`body > .x`）降级为后代选择器；
- 路由激活前执行的布局测量代码可能拿到 0；
- `window.open` 的弹窗特性（width/height）无法在单文件内复现，重写为页内导航；
- 合并基于线性文档解析（非正则），已实测穿透以下陷阱：performance.html 的 SheetJS 脚本字符串内嵌 `</head>`/`<body>`/`</body>` 文本、kb-admin 的 `url(#${id})`、多页 `<style>` 内嵌于 `<script>` 字符串等——正则方案在这些点上会发生内容截断/JS 污染，线性解析器与浏览器行为一致故不受影响。

## 5. 建议

1. **默认不做全量合并**——74 MB 单文件在本项目的访问模式（稀疏、巨页、频繁更新）下五个维度全部净损失。
2. **如要单文件交付，只合并小工具页子集**：report + manual + issues（0.35 MB，零损失，导航从 3 次变 1 次）。
3. **比合并更值得做的优化**（针对性解决真实瓶颈）：
   - qa.html / cc-home.html 的 base64 图片外置为独立文件——利用缓存与并行解码，首屏可先渲染文字框架；
   - 服务端开启 brotli/gzip（文本 73 MB 可压缩至约 1/5，base64 部分收益有限但仍有效）；
   - 共享样式/脚本抽取为 1 个跨页缓存文件，消除 367 个同名 class 的漂移风险，同时保持页级缓存粒度；
   - 保留并宣传 `sw-quiz.js` 的离线能力——它已提供页级 stale-while-revalidate，恰是合并方案最弱的维度的现有解。
