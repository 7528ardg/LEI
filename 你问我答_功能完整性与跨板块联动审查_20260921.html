3.2 双向跳转的健壮性设计（已核实，值得保留）

  • 归属过滤：跳转上下文带 to 字段，接收侧比对自身模块名后才认领，避免「谁先醒谁消费」——该问题在 2026-09-19 已被实测抓到并修复。
  • 双通道互补：URL 参数（独立打开）与 localStorage（壳层内嵌）并存；后者补了 storage 监听，解决「目标 iframe 早已加载、DOMContentLoaded 已过」的空转。
  • 消费即清 + TTL：避免下次手动打开误弹旧提示。
  • AI 来路桥接：落地页以包装 fetch 的方式给 chat/completions 补 system 提示，不耦合各板块各自的 AI 客户端实现。

四、问题清单

P0 高危绩效数据跨板块联动被 AES-GCM 加密阻断，你问我答读不到绩效后台的真实数据
现象
在「绩效管理」录入数据后，到「你问我答」提问绩效相关问题，问答层判定「该月无数据」，无法给出任何真实分数。
根因（写入侧）
绩效管理 performance.html:12693 saveMonth() 落库前经过加密： 
let encrypted;
try { encrypted = await DataEncryption.encrypt(data); } catch(ex) { encrypted = data; }
await set(DB_PREFIX + monthKey, encrypted);   // 键：crew_gz_2026-08
DataEncryption.encrypt()（:13866）在密钥可用时返回 'ENC:' + base64(iv+ciphertext)；无密钥才回退明文。
根因（读取侧）
你问我答 qaLoadRealPerf()（qa.html:9170）按明文结构直读同一 IndexedDB 键，qaMapRealMonth()（:9136）取 monthData.summary： 
const sum = (monthData && Array.isArray(monthData.summary)) ? monthData.summary : [];
// monthData 实为字符串 "ENC:..." → monthData.summary === undefined → sum = [] → 返回空
qa.html 全文 decrypt 出现 0 次、ENC: 感知 0 次。
触发条件（已实测确认必然触发，不是偶发）
file:// 下实测 window.isSecureContext === true、crypto.subtle 可用、AES-GCM 加密调用成功。因此本地直开、PWA(HTTPS)、APK 三种场景下加密均生效，无一例外。绩效管理源码中那句「crypto.subtle 不可用，跳过加密」的告警分支，在现行浏览器下不会被走到。
复现证据（单元级）
抽取 qa 侧映射函数到 vm 沙箱，同一输入两种形态对比： 
明文结构  → 1 条，首条绩效总分 88.5，_来源 "绩效后台"
密文形态  → 0 条   ← 静默丢弃，不抛错、不打日志
qa_has_decrypt: false    qa_reads_ENC_prefix: false
perf_prefix_marker: true perf_returns_plain_when_nokey: true
影响范围
  • 你问我答的全部绩效类问答对绩效后台数据不可见（姓名+月份查分、排名、完成率等）。
  • 连带影响跨数据注入 AI 上下文（perfHint()）的质量，AI 兜底在缺少真实分数时存在给出误导性回答的风险——这正是源码注释自己警示过的「变相编造」场景。
  • 「绩效脏标记」通路本身工作正常（更新能触发重载），但重载后拿到的仍是密文，故障表现为静默：无异常、无日志，只有答不出。
  • 缓解：qa 侧手工「导入数据」通道（qa_perf_data_v1）仍可用，用户手动导入即可恢复问答能力。
为何既有的 17 项绩效联动回归没拦住
_verify_perf_linkage.js / _verify_perf_real.js 都在测试侧用内存 mock IndexedDB 灌入明文结构，绕过了 Storage.saveMonth() 的真实加密路径，属自证式测试——它验证了「映射层正确」，却没验证「真实存储形态可被映射层消费」。
修复建议（按推荐度）
  1. 推荐——绩效侧落库时同步写明文镜像：saveMonth() 成功后额外写 localStorage['qa_perf_mirror_v1']（只含问答所需字段：姓名/月份/各项得分），qa 优先读镜像、IndexedDB 作兜底。改动最小，不把解密能力扩散到消费端，且天然与 qa 现有 qaReadUploadedPerf() 通道契合。
  2. 可行——qa 侧复用同一密钥自行解密：绩效密钥本就存在 localStorage['gz_perf_enc_key_v2']（跨板块共享），qa 可复制一份 decrypt 实现。缺点是解密逻辑双份维护、易再次漂移。
  3. 备选——去掉绩效数据加密：若加密仅是合规姿态而非硬要求，可评估移除，但需产品侧确认。
无论选哪种，都必须补一条「真实存储形态 → 消费端可读」的端到端断言（走 saveMonth() 真实写入，而不是 mock 明文），否则同类断裂还会复发。

P2 低危反馈回归脚本引用已删除的函数，回归链路失效
现象
_verify_qa_feedback.js 退出码 2：ReferenceError: qaFbSyncEnabled is not defined，脚本在第 11 条断言处中断（前 10 条均通过）。
核实
qaFbSyncEnabled 在 qa.html 中出现 0 次——云同步能力已下线，测试脚本仍在断言该变量恒为 false。属测试债务，产品功能本身正常（点赞、吐槽、改良答案、v1→v2 迁移、零网络请求前 10 项全部通过）。
影响范围
该脚本作为常驻回归会持续非零退出，若被构建链守护引用，会掩盖真正的回归失败信号（狼来了效应）。
建议
把该断言改为「源码不含云同步相关标识符」的静态检查，或直接移除该条。
P2 低危两个壳层回归脚本硬依赖未启动的本地服务

建议

六、总体结论

功能完整性：可用。六库 3476 条数据字段完整、无空题干空答案；问答核心、答案工具条、个人面板、CBT 练习、反馈闭环、记忆与会话、AI 兜底七条主功能线均有实测证据支撑；构建守卫 42 项全过。

跨板块联动：6 条通路中 5 条健康、1 条断裂。知识库双协议（旧覆盖层 + 新数据包）、向 9 个板块的跳转落地、CC 之家直达、壳层深跳——这四条最易出错的链路全部实测通过，且具备归属过滤、TTL、消费即清等健壮性设计，实现质量较高。

唯一的系统性风险集中在「绩效管理 → 你问我答」这条数据链上：写入侧加密、读取侧按明文解析，两者从未在同一条真实路径上被验证过。由于触发条件是「crypto.subtle 可用」而该条件在当前浏览器下恒为真，这不是边缘 case，而是当前线上必然发生，且表现为静默答不出、无任何报错。

建议处置顺序：① 先按 §4.1 方案一打通绩效数据并补真实路径断言；② 发布前核对 APK/PWA 与源的功能标记对齐；③ 清理 §4.3、§4.4 两条测试债务，让常驻回归重新具备可信的失败信号。

本报告由静态契约核对、端到端实测与单元级复现三类证据交叉支撑，所有结论均可复算。
